## mainframe.as (189 строк)

**Назначение.** Базовый файл работы с основным окном Конфигуратора (заголовок mainframe.as:3 — «Тут часть кода, работающая с основным окном»). При создании платформой главного top-level frame (событие `eventCreateFrame`) запоминает ссылки `mainFrame`/`coreMainFrame`, регистрирует подписчика на «простой» (idle) платформы и запускает пакеты уровня `piOnMainWindow`; на первом простое — пакеты уровня `piOnFirstIdle`. Даёт остальному движку три ключевых механизма: отправку команд в главный фрейм (`sendCommandToMainFrame`), запрос состояния команд (`getMainFrameCommandState`/`commandState` через копию `ICommandState`) и очередь отложенных дел (`idleHandlers`, `idleHandlersSingle`, `wakeIdle`).

**Инициализация.** Пакетов `Packet(...)` файл не создаёт. Точка входа — `void initWorkWithMainFrame()` (mainframe.as:10-12), вызывается из `run()` в main.as:37 (до него инициализируются пути и профиль). Она подписывает объект `EventTopLevelFrame` на событие создания фрейма:

```
getEventService().subscribe(eventCreateFrame, AStoIUnknown(EventTopLevelFrame(), IID_IEventRecipient));
```

Глобальные объекты (mainframe.as:14-15):
- `ITopLevelFrame&& mainFrame` — главное окно (заполняется один раз);
- `ITopLevelFrame&& coreMainFrame` — «ядрёный» фрейм из `mainFrame.getCoreTopLevelFrame(coreMainFrame)`; именно у него берётся `ICommandReceiver` (`coreMainFrame.unk`).

Объектов `OptionsEntry` нет.

**Типы.**

### `class EventTopLevelFrame` (mainframe.as:17-37)
Приёмник события `eventCreateFrame` (интерфейс `IEventRecipient`).
- `void onEvent(const Guid&in eventID, int_ptr val, IUnknown& obj)` — приводит `obj` к `ITopLevelFrame&&`; пишет в `dbgLog` («объект не приводится…» / «frame получен, тип=…»); если `mainFrame` ещё пуст и `frame.frameType() == eTLFT_Main`:
  1. `&&mainFrame = frame; mainFrame.getCoreTopLevelFrame(coreMainFrame);`
  2. создаёт `IdleHandler`, оборачивает `AStoIUnknown(IdleHandler(), IID_IIdleHandler)`, делает `AddRef()` и `getIdleService().addIdleHandler(ih)`;
  3. `wakeIdle()` — комментарий: «первый простой (загрузка аддинов, восстановление окон) не должен ждать клика пользователя»;
  4. `initPackets(piOnMainWindow)` — запуск всех пакетов уровня главного окна (packets.as).

### `class MyCommandState` (mainframe.as:40-74)
Реализация интерфейса `ICommandState`, который 1С опрашивает при запросе состояния команды. Поля: `CommandID idCopy = CommandID(IID_NULL, 0)` (копия ID команды — комментарий mainframe.as:41-42: раньше здесь была ссылка `_idc`, которую никто не заполнял, `id()` обращался к null и 1С падала в frame.dll), `int p`, `bool bEnable`, `bool bChecked`, `string text`, `string descr`, `string tooltip`. Методы:
- `int_ptr id()` — возвращает `idCopy.self` (комментарий mainframe.as:55: на x64 адреса — `int_ptr`, `uint` обрезал указатели, и 1С падала в frame.dll на «списочных» командах);
- `int param()` — возвращает `p`;
- `int_ptr object(int_ptr i)` — `mem::int_ptr[i] = 0; return i;` (обнуляет выходную ячейку);
- `void enable(bool enable)`, `void setCheck(bool check)`, `void setText(const v8string&)`, `void setDescription(const v8string&)`, `void setTooltipText(const v8string&)` — заполняют поля (читаются потом из `CommandState.cmdState`);
- `void u1(int_ptr)`, `void u2(int_ptr)`, `void t1()…t5()` — пустые заглушки остальных слотов интерфейса.

### `class MyCommandStateList` (mainframe.as:76-82)
Реализация `IListCmdState` (состав подкоманд): `uint count`; `void setCount(uint c)` — запоминает число подкоманд (позже отдаётся как `get_subCommands()` в `ICmdUpdateResult`, com_commands.as:35-37).

### `class CommandState` (mainframe.as:84-100)
Агрегат состояния одной команды: поля `MyCommandState cmdState`, `MyCommandStateList lstState`, `ICmdStateImpl&& allState`. Конструктор `CommandState(const CommandID& id, bool withList)`:
1. копирует `id.group`/`id.num` в `cmdState.idCopy`;
2. `currentProcess().createByClsid(CLSID_CmdStateImpl, IID_ICmdStateImpl, allState)` — нативный объект-состояние платформы (`CLSID_CmdStateImpl {6E3B9D91-2921-4B9D-8C25-4E7884FA3B17}`, command.v:114);
3. при включённой трассе vtable (`diagTraceOn("vt")`) — `dumpVtable(&&allState, "ICmdStateImpl")`;
4. `allState.setCommand(id, AStoIUnknown(&&cmdState, IID_ICommandState))`;
5. если `withList` — дополнительно `&&allState.lstState = AStoIUnknown(&&lstState, IID_IListCmdState)` (используется для команд со списком подкоманд, когда `subCommand != -1`).

### `enum stateFlags` (mainframe.as:103-107)
Флаги результата `commandState()`: `cmdStateHandler = 1` (имеется обработчик команды), `cmdStateEnabled = 2` (команда доступна), `cmdStateChecked = 4` (команда помечена).

**Функции файла.**
- `uint commandState(const CommandID& cmd, int subCommand = -1)` (mainframe.as:109-114) — получает `CommandState&&` через `getMainFrameCommandState` и возвращает маску `cmdStateHandler | (bEnable ? cmdStateEnabled : 0) | (bChecked ? cmdStateChecked : 0)`; при отсутствии обработчика — 0. Используется, например, в intellisite.as:672 и ModuleTextProcessor.as:711.
- `CommandState&& getMainFrameCommandState(const CommandID& cmd, int subCommand = -1)` (mainframe.as:116-123) — если `coreMainFrame !is null`, берёт `ICommandReceiver&& cmdReceiver = coreMainFrame.unk` и вызывает `getCommandState(cmd, subCommand, cmdReceiver)`; иначе `null`. Используется colorer.as:120/311/324/1541, com_commands.as:42, keywords.as и др.
- `CommandState&& getCommandState(const CommandID& cmd, int subCommand, ICommandReceiver&& cmdReceiver)` (mainframe.as:125-133) — если приёмник есть и `cmdReceiver.hasHandler(cmd)`: создаёт `CommandState st(cmd, subCommand == -1)`, задаёт `st.cmdState.p = subCommand` и вызывает `cmdReceiver.updateState(cast<IUnknown>(st.allState))` — платформа заполняет состояние; возвращает его.
- `bool sendCommandToCmdRecv(const CommandID& cmd, int subCommandIdx, ICommandReceiver&& pCmdRcv)` (mainframe.as:135-143) — если `pCmdRcv.hasHandler(cmd)`, передаёт `pCmdRcv.transmitCommand(Command(cmd, subCommandIdx))` и возвращает `true`.
- `bool sendCommandToMainFrame(const CommandID& cmd, int subCommandIdx = 0)` (mainframe.as:145-152) — обёртка `sendCommandToCmdRecv` для командного приёмника `coreMainFrame`. Широко используется движком: colorer.as:1542 (переход к определению F12), colorer.as:1818 (toggle breakpoint), keywords.as:256 и StockListInterceptor.as:491 (форматирование блока), ModuleTextProcessor.as:712/723, textwnd.as:623, StockListInterceptor.as:99, com_designer.as:199 (метод `sendCommand` объекта Designer).
- `void wakeIdle()` (mainframe.as:161-164) — `PostMessage(0, 0, 0, 0)`, т.е. `WM_NULL` в очередь потока. Комментарий (mainframe.as:157-160): «простой» (`onIdle`) наступает только после обработки очередного сообщения; если очередь пуста, отложенные на простой дела (первый простой при старте — загрузка аддинов и окон, показ списка подсказки) ждут следующего события — клика или мигания курсора (задокументирован случай «ожидание простоя 1735 мс», окна не разворачивались, пока не кликнешь в окно). `WM_NULL` ничего не делает, но заставляет цикл сообщений сделать оборот и вызвать простой.

### `class IdleHandler` (mainframe.as:165-189)
Реализация `IIdleHandler` (event.v:63-66; интерфейс `{6B1FFDD6-36BE-11D4-9859-008048DA1252}`).
- `bool first = true`;
- `bool onIdle(size_t count)`:
  1. при первом вызове — `initPackets(piOnFirstIdle)` (mainframe.as:170) — здесь стартуют пакеты `pkMainMenu` (mainmenu.as) и др.;
  2. выполняет все функции из `idleHandlers` — «ровно столько элементов, сколько было в массиве на начало вызова» (mainframe.as:174-176): добавленные во время обработки выполнится в следующий раз;
  3. фиксирует `im = idleHandlersSingle.length`, выполняет одноразовые обработчики; если массив не вырос — `resize(0)`, иначе `removeRange(0, im)` (одноразовые, добавленные в процессе, остаются на следующий простой);
  4. возвращает `false`.
- `int unknown()` — возвращает `idleHandlerUnknownFuncAnswer` (mainframe.as:187). Значение определено в event.v:68-73: `7` для `ver <= 8.3.5`, иначе `0`.

**Перехваты.** В файле нет `TrapVirtualStdCall`. (Командный канал `coreMainFrame` перехватывается в других файлах: `ICommandReceiver_transmitCommand` — com_events.as, `ICommandReceiver_updateState`/`hasHandler` — mainmenu.as.)

**Используемые API.** `getEventService().subscribe` (`IEventService {EBF766AA-F32C-11D3-9851-008048DA1252}`), `eventCreateFrame {3573FFE0-2FFF-11D5-BF5E-0050BAE2BC79}` (event.v:81), `IID_IEventRecipient {D15F2BB0-BD08-11d3-B950-008048DA0334}`; `getIdleService().addIdleHandler` (`IIdleService {6B1FFDD4-36BE-11D4-9859-008048DA1252}`, event.v:41), `IID_IIdleHandler`; `ITopLevelFrame`/`eTLFT_Main`/`getCoreTopLevelFrame`; `currentProcess().createByClsid` c `CLSID_CmdStateImpl`; `IID_ICmdStateImpl` (`ICmdStateImpl {70A10FE2-2D9D-4B4F-B157-75F15557BE9D}`), `IID_ICommandState` (`{E4328FC0-D97B-11d3-8A57-008048DA06DF}`), `IID_IListCmdState` (`{8F8095EE-3DF3-4B90-BD15-C06CFF6149AC}`); `mem::int_ptr`; winapi `PostMessage`; `diagTraceOn`/`dumpVtable`/`dbgLog` (diag.as).

**Взаимодействия.** Использует: `initPackets`/`PacketsInitLevel` (packets.as), `dbgLog`/`diagTraceOn` (diag.as), `idleHandlerUnknownFuncAnswer` (event.v). Предоставляет другим файлам: `mainFrame`, `coreMainFrame` (mainmenu.as:421, com_events.as `setCmdTrap`), `sendCommandToMainFrame` (см. выше), `getMainFrameCommandState`/`getCommandState`/`CommandState` (com_commands.as:41-48 — COM-обёртка `ICmdUpdateResult`; controls.as:212/239 — `IV8Form.getCmdState`/`getCtrlCmdState` создают `CommandState` напрямую), `commandState` + `stateFlags`, `idleHandlers` (com_designer.as:74, com_windows.as:20, textwnd.as:757, scriptLoader.as:223), `idleHandlersSingle` (mainmenu.as:297, controls.as:368, StockListInterceptor.as:129/189), `wakeIdle` (там же), класс `IdleHandler`.

**Версионные ветки.** В самом файле блоков `#if ver` нет; единственная неявная — значение `idleHandlerUnknownFuncAnswer` из event.v (7 на 8.3.5 и ниже, 0 на новых).

**Особенности.**
- Ловля главного окна не через перехват, а через штатное событие платформы `eventCreateFrame`.
- `wakeIdle` — дешёвый хак против «зависания до первого события»: очередь пуста → onIdle не вызывается → отложенные дела (окна, подсказки) ждут клика; `WM_NULL` разгоняет цикл.
- `MyCommandState.idCopy` и `int_ptr id()` — два задокументированных x64-фикса падений в frame.dll (усечение указателя и незаполненная ссылка).
- Двухуровневая очередь idle: `idleHandlers` — постоянные подписчики, `idleHandlersSingle` — одноразовые (семантика «выполнить при следующем простое и удалить»).

## mainmenu.as (440 строк)

**Назначение.** Пункт верхнего уровня «Снегопат» в главном меню Конфигуратора (заголовок mainmenu.as:1-8: между «Конфигурация» и «Отладка»; фактически пункты добавляются в панель «Сервис» главного меню). Меню рисует платформа из «панелей» (bands): панель — это `CommandID {группа, номер}`, её содержимое — список пунктов (`CommandID` + вес типа `double`, порядок по весу). Главное меню — панель `{B78F2E80-EC68-11D4-9DCF-0050BAE2BC79}/1`; пункт верхнего уровня — «popup-команда», у которой есть одноимённая панель с подпунктами. Модули платформы дополняют меню так же: создают объект `CommandInterface` (CLSID `F459D5F0-…`), кладут в него панели (`addBand`) и отдают менеджеру панелей (`addSource`). Подробности реверса — `tools/MAINMENU.md` (на момент анализа файла в репозитории отсутствует). Включение: `logs/diag.ini`, `hook.mainmenu=on` (по умолчанию включено на 8.3.27; выключить: `hook.mainmenu=off`).

**Инициализация.** Один пакет: `Packet pkMainMenu("MainMenu", initMainMenu, piOnFirstIdle)` (mainmenu.as:14) — без зависимостей, инициализируется на первом простое (запуск `initPackets(piOnFirstIdle)` — mainframe.as:170). Глобальные переменные (mainmenu.as:92-99, 321-323): `array<uint64> mmAddrs`, `array<MMCall4&&> mmFns` (кеш функторов для `mmCall`), `bool mmDone` (меню построено), `int_ptr mmManager` (адрес менеджера панелей), `bool mmTrapped`, `int_ptr mmGroupBytes` (16 байт GUID нашей группы в памяти), `TrapVirtualStdCall trMMUpdate`, `TrapVirtualStdCall trMMHas`, `uint mmRefreshIdx`, `bool mmConfirmed` (платформа запросила состояние нашего popup — пункт реально нарисован), `uint mmBuildTick`. Объектов `OptionsEntry` нет; управление — через `diagHook("mainmenu", true)` (опция `hook.mainmenu`, diag.as:110).

**Функции файла.**

**Особенности.**
- Полностью реверс-инженерный механизм: платформа не даёт публичного API для добавления пунктов меню, поэтому используются сырые слоты `ICommandService` (11), менеджера панелей (3, 10, 13) и источника (4, 13) с жёсткими смещениями (`MM_MANAGER_OFF=0xD0`, поля записей 0x14/0x28/0x30, `ICmdDescription - 0x70`, +0x68 и т.д.).
- Шаблоны пунктов берутся у живых панелей платформы (`mmTemplate`) — копируются реальные 0x70-байтовые структуры, правятся только id и вес.
- Веса — «необработанные» `uint64`-представления double (100.0/99.0/1.0).
- Подтверждение отрисовки — только побочное: платформа вызывает `updateState` нарисованного пункта (`mmConfirmed`); до подтверждения панели перестраиваются до 60 раз (первые 40 — каждые 2 с, далее каждые 10 с).
- На 8.3.17 вся сборка отложена таймером на 4 с (падение платформы при перестройке на первом простое).
- Риски: на версиях, не перечисленных в mainmenu.as:32-82, функция отключена; смещения не проверены на иных сборках; `mmSetCommandText` пишет прямо в память описания команды.

**Особенности.**
- Обход бага 1С при сохранении формы (большой комментарий forms.as:443-450): «разработчики не учитывали, что файл формы может сохраняться не в составе родительского контейнера, а сам по себе, то для записи в файл для формы используется дефолтная процедура сериализации. Она открывает файл в режиме fomOut… Однако в процессе сохранения формы часть данных читается из файла… 1С зависает». Решение — перехват `IFileSystem_openURL`: файлы `.ssf` при записи открываются на чтение/запись. Следствие: «при создании формы скрипта её надо сохранять исключительно с расширением ssf — snegopat script form».
- `catcher.bypass = true` (forms.as:468) — тонкость: ошибка открытия файла — не та ошибка, которую должен гасить snegopat.dll; это штатный механизм, выше 1С ставит свой обработчик исключения.
- Реверс формата хранилища форм в `findForm`: файл `root` → id md-файла → список форм по GUID-маркеру `d5b0e5ed-256d-401c-9c36-f630cafd8a62` → имя формы регэкспом → файл `<uuid>.0`.
- Патч vtable окна формы с шутливым комментарием «с покером и куртизанками» (forms.as:487-488): копия создаётся один раз (глобальная `customFormVtable`), все последующие скриптовые формы сразу перенаправляются на неё.
- Грубая правка URL в документе (forms.as:92-98): деструктор/конструктор по вычисленному адресу — хрупкое место при смене раскладки `IDocument` (поэтому и вер.-ветка `+36`).
